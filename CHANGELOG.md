# Changelog

## Unreleased

- **Fixed: the ST-LRPS ablation ladder did not measure what it named.** In `hpc/scenarios/…_A0_to_A6.jsonl` the A5 and A6 lines had identical flags (task 6 retrained A5), and no line trained the shipped model. In `lunaris-ablation` A0–A5 set no `--model-preset`, so every arm used the default physical radial-decay encoding; A6 differed from A5 only in the direction weight (0.2 → 0.1), and A7 and the legacy alias `multiscale_siren` resolved to the shipped default. Now A0–A5 train on raw xyz at the shipped loss weights and A6 adds the physical radial-decay encoding, so each step changes one component and A6 is the `TrainConfig` default (a test resolves every step through the training parser). A7, its legacy alias `physical_radial_decay_recommended` and `multiscale_siren` are removed. The HPC file is generated from the registry (`tools/hpc/generate_ablation_scenarios.py`; a test fails when it is stale).
- **Changed: every ablation arm trains on three seeds over one split.** `lunaris-ablation --seeds` (default `42 43 44`; `--seed N` still runs one seed) and `--split-seed` (default the first seed; every run gets the same split — before, a single `--data` file was re-split with each training seed). Runs go to `<out-root>/<arm>/seed<N>/`; the HPC file has 21 lines, seed-major. `st_lrps_ablation_summary.csv` / `.md` now hold one row per arm with mean ± sample std over seeds; per-run rows stay in `ablation_summary.csv` / `.json`. The paper ablation config takes `"seeds"`.
- **Added: `val_accel_rmse_m_s2` / `train_accel_rmse_m_s2` in the training history.** The unweighted residual-acceleration RMS in m/s². `val_loss_a` and the checkpoint score average per altitude bin when `--use-altitude-balanced-loss` is on, so they are not comparable between ablation arms. The ablation summary reports this metric at the best epoch and ranks arms by it (`ablation_ranked_by_val_accel_rmse.csv` replaces the ranking by final validation base loss). Checkpoint selection is unchanged.

- **Fixed: the paper-safe field-evidence gate passed with no field data.** The evidence taxonomy took metric names from the CSV header, and a decomposition block counted as present when its metrics dict existed, so an all-blank `accel_rms_m_s2` column counted as measured field evidence: a trajectory-only benchmark passed `paper_safe`. A column now counts only when at least one row holds a finite value. The `ric` trajectory marker matches as a whole token (it matched `metric_order`, `numeric_*`), and `accel_max_error_m_s2` / `potential_error_m2_s2` are classified as field evidence. Valid benchmark outputs classify as before except those two columns (now field evidence) and `eccentricity` / `extended_metrics_source` (no longer trajectory evidence).

- **Fixed: `--reuse-cache` scored a cache that had no config fingerprint.** It warned and reused the cache, so results computed under an older configuration could be reported as current. Such a cache is now refused unless `--allow-stale-cache` is given; a fingerprinted cache that matches is reused as before.

- **Fixed: ST-LRPS dataset and split guards accepted bad input.** The altitude-stratified split raised "split fractions leave no training samples" when one altitude bin held a single row (now that row goes to train); NaN/Inf altitudes were dropped or put in train by both altitude split policies (now refused); `CloudSuiteConfig` accepted the same seed for `train_uniform_seed`, `val_seed` and `test_seed`, which sample the same shell with the same strategy (a tiny suite with `--val-seed 42` had 2000 of 2000 validation rows identical to training rows; now refused); and an OOD-low band below the surface (`train_alt_min_km - ood_margin_km < 0`) was accepted and only failed at training. Suites generated with valid settings are bit-identical to before.

- **Fixed: run and dataset provenance could record another repository's commit.** `resolve_git_commit` ran `git rev-parse HEAD` in the process working directory, and the dataset contract located the repository with a fixed parent offset that only holds in an editable install. Both now use `lunaris.common.provenance.resolve_repo_commit`, which runs git in the package's own directory and still honours `GIT_COMMIT`.

- **Fixed: smaller ST-LRPS guards.** Orbit drift no longer treats a failed domain check as in-domain (it raises under `strict_domain`, otherwise counts `domain_check_failures`); random benchmark scenarios skip only `ValueError` rejections instead of every exception; a failing benchmark progress callback is logged instead of suppressed; a GM override is checked against the artifact's own GM with `LUNAR_GM_REL_TOL` (5e-4) instead of 20 %; invalid `periodic_eval_dataset`, `periodic_eval_prefer_checkpoint` and `laplacian_mode` values raise instead of falling back silently; the trainer's stop-signal handlers are restored when training raises; a resume reports how many malformed history lines it skipped; and an `alt_min_km` of 0.0 is no longer read as missing.

- **Fixed: orbit drift works for residual artifacts over an SH baseline.** `python -m lunaris.surrogate.st_lrps.evaluation.orbit_drift` refused every residual artifact whose baseline is spherical harmonics of degree > 0, which is the standard kind. Their labels hold degrees (base_degree, target_degree] of the source field (`sh_potential_accel_batch_serial` with `degree_min=base_degree`), so the tool now builds the base as the same file's field through base_degree (`GravityModel.accel_fixed`: the mu/r monopole plus degrees 1..base_degree, with the file's GM and radius) and passes it to `predict_total_accel_fixed`. The file is the one the dataset contract records (`source_gravity_file_path`, else `source_gravity_model`), or `--gravity-file` / `--ref-gravity-file` when that path is from another machine. A file whose sha256, GM or radius differs from the artifact's is refused; for an artifact with no recorded sha256 only GM and radius are checked, with a warning and `sha256_verified: false`. The report records the file and whether its sha256 was verified (`test_base`, `ref_base`). The default reference is still the point mass alone, so for such an artifact the drift includes its degree 2..base_degree field. On a 2-epoch artifact trained on a JGGRX d/o 3-30 suite (50-300 km, 300 test points), total minus SH(30) truth equals the network's own error to 5.6e-16 m/s^2. The old point-mass-plus-network path differed from this total by exactly the dropped degree 2-3 field, 5.4e-4 m/s^2 median.

- **Fixed: a cancelled or preempted training job could force-quit without saving.** `scancel` and preemption signal every process of the job while the batch shell also relays the TERM it receives, so the trainer saw two stop signals at once and the second force-quit (exit 130) before the current epoch was saved. A repeat within 5 s is now the same stop and is ignored; a later one still force-quits. The resume drift warning also no longer hides schedule, checkpoint-metric and runtime-kind settings (`warmup_epochs`, `best_metric`, `runtime_model_kind`, ...).

- **Fixed: a scenario task requeued by Slurm before its first checkpoint was refused.** The requeued attempt ran the launcher with `--resume`, which refused the directory holding only the launcher's provenance. The launcher's new `--restart-if-no-checkpoint` restarts a scenario in a checkpoint-less directory its own `scenario.json` names, and the array template passes it on requeue; other directories are still refused. The single-job resume hint no longer prints an empty `''` argument.

- **Fixed: capped ephemeris tables ended at tf.** With the 60 s table step, a Yoshida run with `output_dt_s` > 60 s and a step above ~65 s (Y8) sampled the force past the extrapolation band at tf and was refused when the tables were built exactly over the run (the CLI adds a 0.1 day buffer). The table now runs on by `output_dt_s - 60 s`; runs with `output_dt_s` <= 60 s build the same table as before.

- **Fixed: the CPU terrain-impact event sampled the nearest pixel by default.** `make_hybrid_impact_event` chose nearest-neighbour when `"near" in kind`, which is true for the default `"bilinear"`, so the terrain clearance jumped at every pixel edge (75.1 m to -28.3 m within 2 ms of flight on the 64 ppd LDEM; the reported event sat at g = -28.3 m). Only a kind starting with `near` selects nearest now; the GPU terrain kernels already interpolate. **Default results change** for CPU terrain-impact times.

- **Fixed: every terrain or albedo sample copied the whole raster.** `_validate_grid_data` converted the grid to float64 on each call: a 2.1 GB copy of the memory-mapped 64 ppd LDEM per sample, measured at 954 ms per sample, which made CPU terrain events inside the switch shell impractically slow. Float32 grids now pass through unconverted (0.1 ms per sample); the kernels promote the four neighbours exactly, so samples are bit-identical (5005 random and edge points, bilinear and nearest).

- **Fixed: a requested terrain or albedo root that did not load was flown as a constant sphere.** `--ldem-root` / `--albedo-root` built the surface provider without strict I/O, so a load failure (e.g. `--ldem-ppd 4` on a root that holds only 64 ppd) warned and continued while the run record listed the root as used. The run now stops (`lunaris` and `lunaris-batch` exit 1 with the reason and the available ppd). Mission Studio passes the same flags: an LDEM root left at the 4 ppd default with only 64 ppd present now stops with that message instead of silently ignoring the terrain. Runs without a root are unchanged.

- **Fixed: the CPU terrain switch shell ignored the impact altitude.** The hybrid impact event switched to terrain clearance 11 km above the 1738.0 km sphere, while the highest LDEM 64 ppd point is 10.157 km above it; with `--impact-alt-km` above ~0.84 km an impact over the highest terrain was found late or missed (2 km impact altitude: a level pass with 1342.8 m minimum clearance was not reported; a -2 deg descent was reported 57.0 s late). The effective switch is now max(configured, highest terrain + impact altitude + 100 m), as the GPU path already does; with the default impact altitude 0 it stays 11 km and event times are identical.

- **Fixed: `TopographyGrid` exposed no pixel-centre latitudes/longitudes.** The surface explorer's maximum-height report and topography plots raised `AttributeError` on every real LDEM product. `lat_centers_deg` / `lon_centers_deg` are now public (16 ppd maximum: 10685.740 m at 5.40625 deg, 201.34375 deg).

- **Fixed: telemetry wrote one print and one file open per trajectory row.** `emit_trajectory` now writes chunks of 1024 lines (one stdout write and one sink append per chunk): 50 000 rows with the telemetry sink 19.18 s -> 5.28 s, with identical stdout and sink content. A failed chunk write still counts one dropped sample per line.

- **Fixed: event epochs and the mission start epoch counted from the first sample, not from `start_date`.** `start_date` is solver time 0, so a run with `t0_s > 0` reported every event and the start epoch early by `t0_s`; a `... TDB` / `... TT` start date was reported as unavailable. They now count from `start_date` in its own time system. `compute_impact_statistics(r_ref_m)` keeps its signature; the radius is documented as unused.

- **Fixed: settings fell back to values that disagreed with their config.** The SciPy runner's rtol fallback (1e-9 vs the config's 1e-10), the two-body baseline tolerances (1e-9/1e-12 vs 1e-12/1e-14), the Nyquist safety default (5.0 vs 4.0) and `plot_all`'s output defaults now read the config or its own defaults. No shipped caller hit them; real-config runs are bit-identical. Canonical ephemeris provider keys now win over the legacy `sun_table`/`earth_table`/`rot_table` names.

- **Fixed: the adaptive integrator stepped over solar-radiation shadow contacts unseen.** The SRP shadow factor has a kink at each penumbra and umbra contact, and DOP853's error estimate shares the stages the kink corrupts, so a step straddling a contact was accepted without its error showing. The lunar engine now declares its shadow contacts (`DynamicsEngine.restart_plan()`: the Moon pair always, the Earth pair with `enable_earth_eclipse`); the SciPy path stops at each contact, re-solves exactly to it so the restart state is a step end, and caps the step across each penumbra (`PENUMBRA_STEPS = 20`). The contact functions (`conical_shadow_angles`, `conical_shadow_boundaries`) use the same float64 operations as the shadow kernel. User events, terminal events and chunk boundaries are reported once and in order across the restarts. Measured on real data (100 km lunar orbit through the Sun direction, SH degree 10, Sun + Earth, A/m 0.1 m^2/kg, 8 h, against DOP853 rtol 1e-13 capped at 0.25 s): Moon shadow 1.8 m -> 2.7e-6 m at rtol 1e-10 and 1.9e-2 m -> 3.6e-6 m at rtol 1e-12; through the 2025-09-07 lunar eclipse 0.18 m -> 3.5e-6 m and 7.3e-3 m -> 1.2e-6 m, at 1.55-1.86x the RHS evaluations. Eclipse event times moved from up to 1.3e-3 s off to within 7e-9 s. Runs with SRP off are bit-identical, including their evaluation counts. Not covered: the fixed-step and batched paths, the occulter switch inside overlapping penumbrae, and the time-only Earth-umbra factor of the facet/quadrature albedo and thermal models. **Default results change** for adaptive runs with SRP enabled.

- **Fixed: the lunar force tables followed the output step, so the output spacing changed the force model.** `build_spice_tables` sampled the Sun, Earth and Moon-orientation tables at `output_dt_s`. For a lunar 100 km orbit, SH degree 60, Sun and Earth, DOP853 rtol 1e-12 and max step 60 s, the 3600 s and 60 s outputs differed by 0.60 mm after 1 day and 10.8 mm after 2 days (inertial frame, solver seconds from `start_date`). The table step is now `min(output_dt_s, 60 s)`: that comparison is bit-identical (0.0 m), and a YOSHIDA4 run at 600 s output matches 60 s output bit-identically. **Default results change** for runs with `output_dt_s` above 60 s; runs at or below 60 s build the same tables as before.

- **Fixed: the first step of a Yoshida run sampled the force before t0 and could be refused.** Y4, Y6 and Y8 sample the force up to 0.35, 0.65 and 0.92 steps before each step start, so the first step read the ephemeris before t0. With the table step capped at 60 s, a lunar YOSHIDA8 run at h = 120 s and 600 s output was refused ("samples the force 109.855 s outside [0, 17280] s"). The first step, including event refinement inside it, is now one DOP853 step at rtol 1e-13 that stays within [t0, t0 + h]; later steps keep the composition, and the coverage guard checks only the overhang past tf. The same Y8 run now completes. **Default results change** for Yoshida runs, first step only: on a lunar 100 km orbit with SH 60 + Sun + Earth and YOSHIDA4 at h = 60 s, the run moves by 7.2e-2 m at t = 600 s and 5.5 m after 1 day (inertial frame, solver seconds from `start_date`); against a DOP853 rtol 1e-12 reference the Y4 error goes from 1025 m to 1020 m. Non-Yoshida methods are unchanged.

- **Fixed: the GM and radius constants named the wrong sources.** The values are unchanged; only the provenance strings were wrong. `MU_SUN` is a pre-DE440 value rounded to 12 digits (5.4e-12 relative from DE440 BODY10_GM). `MU_MOON` is DE440 truncated to 10 digits (9.3e-11 relative). `MU_EARTH` is the WGS-84 value (DE440 differs by 1.6e-8). `R_EARTH_MEAN` is a rounded 6371 km convention, not the WGS-84 mean radius (6371008.771 m). `R_MOON` is the GRAIL field reference radius (1738.0 km), not a LOLA radius; `R_MOON_MEAN` (1737.4 km) is the pck00011 radius and the LOLA offset.

- **Fixed: the engine's surface radiation used a different Moon radius from the standalone wrappers.** The engine built its albedo and thermal-IR facets and its visible-disk quadrature sphere on `R_MOON` (1738.0 km), while the wrappers, the perturbation budget and SRP's Moon shadow use `R_MOON_MEAN` (1737.4 km). The engine now uses the IAU mean sphere, so it reflects, emits and casts its shadow from one Moon. **Default results change** for the engine's albedo and thermal-IR accelerations; the measured thermal-IR change at 100 km altitude (day side) is -0.11 % (2.0e-11 of 1.88e-8 m/s^2). The RHS golden values for the affected scenarios were re-recorded (at most 2.7e-10 relative to the total RHS acceleration).

- **Fixed: the adaptive loss-weighting rule was cited to GradNorm.** `LUNARIS-ALG-OPT-002` (`GradNormWeights`) is the gradient-magnitude-ratio rule of Wang, Teng & Perdikaris (2020, arXiv:2001.04536, Sec. 2.5), adapted to L2 norms, a once-frozen `ntk_init` default and a [0.35, 4.0] clamp. The registry and `references.bib` now cite that paper (`Chen2018GradNorm` is replaced by `Wang2020GradientPathologies`). The dynamic mode's `ema_beta = 0.9` weights the previous value, which is alpha = 0.1 in the paper's convention. `SirenResBlock` moved from the exact SIREN entry to the heuristic entry, because its LayerNorm, skip path and zero-initialised output layer are not in Sitzmann et al. (2020).

- **Fixed: the simple albedo backend ignored `--albedo-const` when a surface provider was attached.** `_prepare_albedo_simple` took the constant from each provider's `as_numba_dict` (its default, 0.12) instead of the configured value. Measured on the old code, `albedo_const = 0.25` with an `InMemorySurfaceProvider` flew 0.12, and the simple-backend albedo acceleration scales linearly with the constant (-52 %). The configured constant now fills the no-map case and cells without data, as the `lambert_facets` path does. Runs whose configured constant equals the provider default are unchanged.

- **Fixed: a maneuver run reported the diagnostics of its last segment only.** For a lunar circular orbit with two 5 m/s burns (3 segments, 39 output rows), the reported `n_points` was 12 and `nfev` 218. The run now reports `n_points` of its own rows (39), the summed `nfev` over all segments (735), and, because energy and angular momentum change at a burn by design, the worst segment's drift and spread, labelled `drift_scope = "worst_segment"`.

- **Fixed: the Earth J2 constants were not the EGM2008 values.** The config factory, `ensure_model_configs` and `EarthJ2Params` used `J2 = 1.08262668e-3`. From ICGEM EGM2008 (fully normalized, tide-free), C20 = -0.484165143790815e-3, so J2 = 1.0826261738522227e-3; the old value is 4.7e-7 relative off. `EarthJ2Params()` also paired J2 with the WGS-84 radius (6378137.0 m) instead of EGM2008's 6378136.3 m (2.2e-7 relative in the J2 acceleration), so the perturbation budget and the engine used different fields. Both constants now live in `common/constants.py`. **Default results change** for runs with the Earth J2 term: about 3e-17 m/s^2 at a lunar orbiter (|a| <= 6.5e-11 m/s^2).

- **Fixed: a manual encoding flag without `--model-preset` silently replaced the model preset.** `--use-fourier`, `--use-sh-encoding`, `--use-radial-*` and `--use-real-sh-basis` switched the default preset (`recommended_physical_radial_decay`) to `custom`, and `apply_model_preset` did the same for programmatic configs. The trainer CLI now exits with a usage error that names the flags and asks for an explicit `--model-preset` (`custom` for manual encoding ablations), and `apply_model_preset` raises on any preset/manual-flag conflict. All 21 scenarios in `hpc/scenarios/*.jsonl` resolve to an identical `TrainConfig` (all 159 fields) before and after. **Default results change** for a run that passed a manual encoding flag without `--model-preset`: it now stops with a usage error instead of training a custom architecture.

- **Fixed: an apsis that fell on an impulsive burn epoch was lost.** The pre-burn segment ended just short of the apsis, and the post-burn segment read its start on the apsis as "not an event", so DOP853 and RK4 both dropped it. Measured on an e = 0.25 lunar orbit: 0 of 1 apoapsis with a 10 m/s in-track burn at the apoapsis epoch, and a zero-dv plan with a burn at every apsis over 2.9 periods reported 0 of 2 periapsides. Apsis events of a continuing segment now start on the side the previous segment ended on. The first case reports 1 of 1 within 1e-6 s of the two-body oracle, and the zero-dv plan keeps every count. Runs without a plan are unchanged.

- **Fixed: the strict lunar RHS called helpers compiled with fastmath.** `accel_j2_oblate_diff_numba` (with its two helpers) reassociates a difference of two nearly equal terms and may drop NaN checks; `accel_solid_tide` and `_normalize_axis_or_default` carried the same flag. All five now use `fastmath=False`. Measured on 5000 random lunar-orbit / Earth geometries, 12677 of 15000 differential-J2 components changed, each by at most 6.4e-13 relative to the term (|a| <= 6.5e-11 m/s^2). **Default results change** for lunar RHS evaluations, by that amount. A test now fails if any fastmath helper is reachable from the RHS.

- **Fixed: the CPU batch propagator accepted a nonzero time origin and shifted every trajectory.** It integrated each sample from `time.t0_s` but resampled onto an output grid that starts at t = 0, so a nonzero `t0_s` clamped the first `t0_s` seconds to the initial state and shifted the rest. The batch engine already refused it; `CPUBatchPropagator` now refuses `t0_s != 0` too, for direct callers.

- **Fixed: the lunar engine counted the geodetic precession twice.** `external_1pn_components` (CPU) and `_external_1pn_cuda` (numba CUDA) added each external body's differential Schwarzschild term to its de Sitter term, but the differential term's velocity-dependent part already precesses an orbit at the geodetic rate. Measured independently on a polar lunar orbit (orbit-averaged torque, Moon-centred inertial axes): either term alone gives 1.0000 Omega_dS (Sun: 19.19 mas/yr), the old sum 2.0000. The external term is now the de Sitter term alone (the local-frame composition of IERS TN 36 Eq. 10.12) on both paths, and the docs and batch diagnostics that listed the differential term are corrected. **Default results change** for lunar 1PN when relativity is on: the removed term was 1.3e-11 m/s^2 (Sun) and 3.1e-13 m/s^2 (Earth) at r = 1838 km, and the `sh_relativity_1pn` RHS golden values moved by up to 1.285e-11 m/s^2 and were re-recorded.

- **Changed: the trainer and evaluator refuse abbreviated option names.** Both parsers used argparse's default `allow_abbrev=True`, so any unique prefix (for example `--epoch` for `--epochs`) was silently bound to that option, and a typo or a flag from another tool could change a run's configuration without an error. The trainer's explicit-preset check also missed an abbreviated `--model-preset`. Both parsers now set `allow_abbrev=False`. A scan of every `--flag` token in the repo's hpc, tools, docs, tests, src, examples and validation trees found no command line that relies on an abbreviation.

- **Fixed: batch propagators drifted off the step grid because they advanced time with a running sum.** The shared batched RK4 loop used `t_curr += dt_eff` for the force evaluation (ephemeris, orientation) and the terrain impact segment start, and the numba_cuda_sh propagator (`GPUBatchPropagator`) did the same. At a non-representable step the sum leaves k * dt: 5.0e-11 s after 700 steps of 100/14 s, and 1.3e-3 s after a year of 60/7 s steps. The clock is now `float(global_step) * dt_eff`, bitwise equal to the sum wherever `dt_eff` is exact in binary (60 s, 10 s, 1 s), so default runs do not move. A resumed chunk recomputes the clock from the saved `global_step`, so a checkpoint written by the old loop still loads and resumes bit-identically to an uninterrupted run; the `batch_checkpoint` docstring is corrected to match. `core/batch_propagator.py` keeps its own running-sum loop, which this change does not touch.

- **Fixed: SciPy events at a chunk boundary were dropped.** Each chunk after the first treated its start as lying on the event surface, so a root at or just past a boundary was lost. For `chunk_s = T/2` from a periapsis (every boundary an apsis) over 3.2 periods, 0 of 3 periapsides and 0 of 3 apoapsides were reported; now 3/3 and 3/3, matching the unchunked run within 1e-6 s. `chunk_s = T/4` and 1000 s also match. Each chunk now seeds its events from the side the previous chunk ended on, and a root the previous chunk reported is not reported twice. The first chunk and unchunked runs are unchanged.

- **Fixed: a CUDASIM batch run failed while building its diagnostics.** The Numba simulator reports device memory as `inf`; `GPUBatchPropagator` stored it and `diagnostics_snapshot` cast it to int, raising `OverflowError` after a successful propagation. A non-finite reading now counts as unknown, `(0, 0)`, as a failed memory query already did; the batch-size budget then uses the configured VRAM budget.

- **Fixed: `GravityModel.from_arrays` dropped the high-degree terms of a rectangular coefficient block.** The degree was bounded by min(rows, cols) - 1 of the C/S blocks, so a (21, 5) block requested at degree 20 became a degree-4 model and silently dropped every term above degree 4. The degree is now limited by the rows only; `slice_gravity_model` already zero-pads the orders. The rectangular model now matches the zero-padded square model to <= 1e-15 relative in `accel_fixed`; square inputs are unaffected.

- **Fixed: spatial-cloud generation oversubscribed a cluster allocation by default.** `SpatialCloudConfig` defaulted `workers` to `os.cpu_count()`, which on a cluster node reports every core of the node rather than the job's allocation. The default now uses the process's affinity mask (`os.sched_getaffinity(0)`) where it exists, and falls back to `os.cpu_count()` on Windows and macOS. Explicit `--workers` values are unchanged.

- **Fixed: CPU batch samples did not inherit the template's strict fixed-degree setting.** `CPUBatchPropagator._make_sample_dynamics` built each sample's `DynamicsEngine` without `strict_fixed_degree`. A paper-safe or strict batch template forbids the adaptive SH blend, so a strict CPU batch could blend the degree with altitude instead of refusing the configuration. Each sample engine now takes the template's value.

- **Fixed: a root exactly on a step end was reported twice.** `solve_ivp` reads an event value of exactly 0 at a step end as a crossing both at the end of that step and at the start of the next. Reproduced on DOP853 with a root on a step end: 2 roots at one time. When the previous step end is finite and non-zero, the step-consistent event wrapper now records that exact zero as the smallest normal float on the side away from it, so the step that reaches the root reports it once (1 root). Values that are never exactly zero are untouched, so runs without such a root are bit-identical.

- **Fixed: the ST-LRPS Studio Periodic Evaluations table showed `-` for RMSE U, RMSE a and Angle.** The training loop writes these values nested under `metrics`, with the angle named `mean_ang_deg`, and the Studio reader looked only for flat keys. The reader now reads the nested form first and keeps the flat form as a fallback. Column headers carry their SI units (m²/s², m/s²).

- **Fixed: adaptive-degree runs could be planned on a full-degree GPU kernel.** The `numba_cuda_sh` and torch classic-SH kernels evaluate the full requested degree everywhere, while the CPU engine blends the degree with altitude when `gravity.adaptive` is enabled, so an adaptive run flew a different field on the GPU. With SH on and `gravity.adaptive.enabled`, both backend policy lists now carry `adaptive SH degree`: an auto or GPU request falls back to `cpu_sh` with that reason in the plan warnings, and the strict posture (`sh_fallback_policy='error'`, paper-safe) refuses it at planning time.

- **Fixed: the SH latitude derivative cancelled near the polar axis.** `sh_potential_accel_batch_serial` (`GravityModel.potential_accel_fixed`, the ST-LRPS dataset generator) formed dP/dphi as `(-n s P + (n+m) k P_{n-1,m}) / cos(phi)`, which cancels near the axis. On a degree-30 random field (Moon-fixed, r = 1750 km) the error against `accel_fixed` was 6.7e-5 m/s² (11 % of the transverse field) at rho = 2e-8 m, 1.3e-6 m/s² at 1e-6 m and 1.3e-9 m/s² at 1 mm. The derivative now uses the same-degree order recurrence of the propagation kernel. The potential is bit-identical on the tested points, and the acceleration is within 1.1e-15 relative of `accel_fixed` for rho from 1e-12 to 1e3 m. **Default results change** only near the polar axis: at rho >= 1 km the change is <= 7.9e-17 relative.

- **Fixed: the provider's residual potential ignored `a_sign`.** `SurrogateGravityModel.predict_potential_and_acceleration_fixed` returned the network's raw dU as the residual potential, while the residual acceleration is `a_sign * grad(dU)` and the baseline potential follows the geodesy convention (a = +grad U). For `a_sign = -1` the total potential's gradient disagreed with the total acceleration, so energy and conservativeness checks on the total field were wrong; `a_sign = +1` was unaffected. Both the canonical-runtime and local autograd paths now return `a_sign * dU`. Tests compare a central difference of the total potential with the returned acceleration for `a_sign = -1`.

- **Fixed: SciPy event root-finding crash on circular orbits.**

- **Added hardware-independent compute accounting to ST-LRPS training, so "how much compute this architecture does" is portable across machines.** Wall-clock time ("training took 5 hours") is not comparable — the same run is 2 hours on one GPU and 10 on another — so the new `surrogate/st_lrps/training/compute_accounting.py` reports the field-standard unit instead: total training **FLOP** and its time-scaled form **petaflop/s-days** (1 PF-day = `8.64e19` FLOP, the OpenAI "AI and Compute" unit).
